02

The v2 thesis

Three moves. Each one removes an entire class of cost rather than shaving a constant.

Core

Typed, insertion-ordered field slice

Event storage becomes a discriminated-union field slice: kind + int64/float64/string/any slots. No map, no scalar boxing, no clone per write, no mutex (request-confined).

Deterministic order becomes a property of the data structure — so DeterministicOrder, key pools, and sorting are deleted from every adapter.

Output

happycontext owns its writer

Fork zerolog’s JSON encoder (MIT, ~800 LOC of non-test encoder code) into internal/, ship hc.NewJSONSink(io.Writer) — zero third-party dependencies, single buffered write per event, byte-compatible with today’s zerolog adapter output.

New users install no logger library at all.

Surface

One lifecycle, compiled once

hc.Compile(Config) clamps and precomputes at middleware construction; hc.Start + op.End(&err) is the only lifecycle. The parallel begin/finish path and its hydration move internal.

~40 exported symbols in the root shrink to the set people actually use.

Why fork zerolog specifically

  • Smallest correct core — internal/json appender suite ≈ 800 LOC non-test
  • Buffer-append style matches append-at-Add — no reflection
  • Output continuity — byte-compatible with what zerolog adapter users already ingest

Why not the alternatives

  • Pre-encoded JSON buffer as Event store — breaks bridge/sampler field access or forces dual storage; one representation beats a faster one nobody can read
  • Fork zap — larger, reflection-centric encoder core
  • Fork phuslu/log — fastest in microbenchmarks, but no output-format continuity; the win we want is the encoder, which the zerolog fork gives anyway

The same request today — v0.4.0, ~1,000 ns · 26 allocs

  • 1Middleware: context.WithValue — box the event into an interface, allocate
  • 2Start: allocate Event + map[string]any(8), insert header fields — every non-trivial int boxed
  • 3Handler: two hc.Add — mutex, map writes, more boxing
  • 4Finish: re-hydrate start fields (RLock, re-read map), select policy, validate levels, second time.Now()
  • 5Write three completion fields into the map — duration_ms boxes an int64
  • 6Snapshot: maps.Clone the whole field map so the sink can own it
  • 7Adapter: iterate the map (random order), pool + sort keys, convert each value through reflection
  • 8GC later: ~2.6 KB and 26 allocations to collect, per request

The same request in v2 — target ≤ 350 ns · ≤ 8 allocs

  • 1Middleware: one context.WithValue (kept — it's the contract) + claim a pooled event, append header records
  • 2Handler: two hc.Add — two typed record appends, ~10 ns each, zero boxing
  • 3End: outcome resolution, three completion records — no map, no hydration, no second clock read
  • 4Policy: precomputed in the compiled runtime — a lookup, not a validation pass
  • 5Sample on scalars + Lookup; drop → recycle buffer, done at ≤ 100 ns
  • 6Commit: Record wraps the buffer zero-copy — no clone, ever
  • 7Encode: one forward pass, SWAR escaping, precomputed prefix, single Write
  • 8Buffer zeroed and pooled — steady state approaches zero garbage per request

The emitted JSON line is the same shape either way — v2 changes what happens before the line exists, not the line. That is the whole trick: the event was never a map that needed cloning, converting, and sorting; it was always an ordered list of facts about one request.

03

v2 architecture

One representation flows from hc.Add to the destination with zero conversion on the first-party path, and a single type-switch on bridges. The WAL drain (W11) is an opt-in detour that decouples request latency from sink health.

04

WAL — the request is the log

The request itself is the WAL — in-memory, per request, no disk

Every hc.Add during a handler appends one typed record to a pooled, request-confined buffer: no map, no lock, no boxing — ~10 ns and 0 allocs steady-state (today's map insert under the mutex costs ~30–80 ns). op.End is the commit point: one pass encodes the log into the final event, writes it, and recycles the buffer. Duplicate keys keep v0 last-write-wins semantics via a short scan; oversized logs grow for correctness and recycle only under the pool cap.

hc.Add(ctx, "user_id", …) → record #1 appended → hc.Error(ctx, err) → record #2 appended → op.End = commit → encode once → write → buffer → pool

Black-box timeline (optional): record positions are implicit sequence numbers, so a policy can emit the log itself as a steps array ({"seq":3,"t_ms":412.1,"k":"db.query"}) for slow or failed requests — zero cost when unarmed, ~32 ns per record once armed (one time.Now() each). This one structure is also what W12 reads mid-request, and it is precisely the W3 typed core — two read patterns, one representation.

How a request flows through the WAL — every call, in order

1

hc.Start(ctx, rt, start) ~0 allocs pooled

A pooled buffer is claimed and reset (records[:0]), header records are appended (op.domain, op.name, op.id, …), a slot is registered in the active-set for the watchdog, and the context now carries the event. Everything downstream — middleware, handlers, anything with ctx — appends to this one log.

2

hc.Add(ctx, key, value, …) ~10 ns · 0 allocs

The value is type-switched to a typed record (see layout below) and appended. Strings and keys copy only their 16-byte headers — no bytes move. Adding the same key twice overwrites that record in place (short scan): v0's last-write-wins semantics, and the log stays deduplicated so the encoder remains a single forward pass.

3

hc.Error / SetMessage / SetLevel / AddRawJSON

The error is stored as a record — its structured form (message, type, cause.*) is materialized once at encode time. Message and level live in the scalar header. AddRawJSON stores pre-encoded JSON verbatim; the escape scan is skipped for it entirely.

4

[background] watchdog arms on stall zero cost until armed

A per-Runtime ticker scans active-set slots. An operation past InflightThreshold emits operation_stalled carrying the WAL tail — the log so far, in order — and flips the event to guarded mode: from now on each append also records t_ms. This is the read pattern that makes hung and OOM-killed requests visible.

5

op.End(&err) — the commit point

Outcome resolves as panic > error > explicit > 5xx > success; three completion records are appended (duration_ms, op.code, op.outcome); the level comes from the compiled policy merged with any requested floor. Nothing has been encoded or written yet — the whole request was "ahead," exactly like a database WAL before its checkpoint.

6

sampling decision drop path ≤ 100 ns total

The sampler sees scalars plus Lookup — never the records slice, never a lock. A dropped event appends nothing, encodes nothing, releases its slot, and the buffer goes straight back to the pool.

7

sink.Write(rec) → pool encode ~25 ns/field

The Record wraps the buffer zero-copy (read-only, valid during the call). The JSON sink encodes all records in one pass — SWAR escaping, precomputed level prefix, timestamp from the reused start reading — and issues a single write. Bridges iterate the same records into native fields. Then: slot released, buffer zeroed ≤ cap and pooled; oversized requests keep their allocation rather than polluting the pool.

The record — one per Add, ~64 bytes

type record struct { key string // field name — header copy, no bytes move kind uint8 // string|int|float|bool|time|dur|err|raw|any num int64 // ints, bools, unix-ms, durations flt float64 // floats str string // string values (header only) any any // fallback: error, raw JSON, structs (rare) }

Rules of the log

  • ▸Append-mostly, one writer. The request goroutine owns the log; no lock exists on the fast path.
  • ▸Insertion order is emission order. Deterministic output is structural — no sorting anywhere downstream.
  • ▸Exactly two readers: the commit encoder at End, and the watchdog snapshot — never concurrent with appends (guarded mode serializes the rare armed case; the fast path never touches that mutex).
  • ▸Bounded recycling. The pool takes buffers back only up to a cap; bigger requests keep their allocation — correctness first.

Timeline arming — how timestamps come to life on a slow request

t=0 Start — no timestamps, zero per-Add cost → t=2.0s threshold crossed → armed: each Add now records t_ms (~32 ns) → t=3.8s End → commit

In the emitted steps array, records before arming carry seq only — sequence is the array position, so it's always known — and records since arming carry seq + t_ms. Late arming loses nothing that matters: the tail is where the slowness lives, and the tail is exactly what got timestamped.

W11 · S/M

Buffered sink — WAL-style async drain

Problem: blocked sink ⇒ blocked request goroutine

Opt-in hc.BufferedSink wrapping any sink or writer:

  • Finalized records are pre-encoded (W4/W8) and appended to a bounded ring — a memcpy plus index bump; never blocks, never encodes twice
  • One background drainer batch-writes buffered lines
  • Ring full ⇒ drop-oldest + dropped counter via stats hook — never block, never grow unbounded
  • Flush(timeout) + flush-on-signal helpers for graceful shutdown
  • Crash window: undrained lines are lost on hard exit — same trade as zerolog diode / zap BufferedWriteSyncer, and the reason W12 exists
W12 · M · data-gated

In-flight records — literal write-ahead

Problem: requests that never end leave no event at all

Reads the in-request WAL tail — the log so far, in append order, timeline if armed:

  • Watchdog flush (first): active ops register in a pool-slot set (one index append); a timer emits operation_stalled past InflightThreshold (off by default, e.g. 10s) with the event’s current fields — zero steady-state cost, catches hangs and kills
  • Eager start records: emit operation_started at begin — doubles volume, viable only per-domain via policy for low-QPS, high-stakes domains
  • Correlation via op.id; end records supersede start/stall records in consumers
  • Both additive — completion path untouched
✕ REJECTED

Durable disk-backed WAL. Append-only file, fsync policy, rotation, permissions, disk-full behavior — that is log-shipper territory (Vector, Fluent Bit), not a Go logging library, and it would dwarf the rest of v2 in maintenance. The buffered sink’s crash-loss window stays documented; users needing durability run a shipper.

The any-fallback race — whole-event map marshaling vs the typed core (12-field payload, M4/arm64, Go 1.27)

The SIMD/JIT libraries (sonic: JIT + AVX2 on amd64; goccy: compiler-based) are built for whole-struct marshaling — goccy wins ~2× on flat maps but both lose to the Go 1.27 stdlib on nested maps on arm64. Their advantage is payload- and platform-dependent, which is exactly why they stay out of the core. The ~140× gap between any map marshaler and the typed loop is the single strongest justification for W3/W4. Users with struct-heavy any fields can still plug their own marshaler via the encoder interface.

ADOPT

Encoder & write path

Hybrid SWAR escape scan · precomputed {"level":"info", prefixes · RawJSON field kind (skip re-escaping pre-encoded blobs) · encode-once multi-sink reuse via Record byte cache · batch drain with single Write + net.Buffers writev (phuslu documents ~10× under load) · shortest round-trip floats (~25 ns via strconv).

EVALUATE

Assembly SIMD & json/v2

True AVX2/NEON escaping (go:build-tagged, like sonic/goccy on amd64) — only if post-v2 profiles show escape scan > 5% of lifecycle. Go 1.27 ships json/v2 as the default encoding/json backend, so our any fallback gets faster free with the toolchain bump. Also rejected: jsontext as primary encoder (~45% slower on clean strings — the race table above) and the arenas experiment (still restricted; pooling already reaches near-zero allocs).

REJECT

goccy & sonic as deps

Measured (§05 table): goccy wins ~2× on flat maps, but both it and sonic lose to the Go 1.27 stdlib on nested maps on arm64 — platform- and payload-dependent wins don’t justify the dependency. The ~140× gap to the typed loop is the argument for the core, not for a library. Pluggable via the encoder interface for users who want them.

⚠ CAUTIONARY

Fast because wrong

The first SWAR prototype benchmarked 3× faster than everything — because a subtly wrong zero-byte detector (missing &^x term) meant it silently skipped escaping entirely. Benchmarks smiled; output was corrupt. Only a 200k-case property test caught it. This is why equivalence + fuzz tests are hard gates for W1, not nice-to-haves.

06

Workstreams

Effort: S < M < L. “break” marks breaking changes; “add” marks purely additive features.

W1

Fork the encoder + SWAR scan

S/Madd

Vendor zerolog v1.34.0’s internal/json (MIT, attributed), add a pure-Go SWAR escape fast path (−11–18% on clean ASCII, measured), and keep a jsontext fallback backend behind an internal interface. Property test + fuzz are hard gates — see §05’s cautionary tale.

W2

First-party JSON sink

Sadd

hc.NewJSONSink(w) on today’s map-based Sink interface — additive, lands as v0.5.0. Puts the forked encoder into production soak before anything breaks. Users can drop their adapter dependency immediately.

W3

Typed Event core

M/Lbreak

[]field discriminated union + scalar header; hc.Add appends typed fields with zero boxing; request-confined (no mutex); events pooled so steady-state allocs approach zero. The breaking heart of v2.

W4

Record + sink contract v2

Mbreak

Sink.Write(ctx, rec *Record) — the slog.Handler.Handle shape: a read-only, insertion-ordered view valid during the call, carrying the operation's real context. No owned map, no clone: 2–4 allocs and 300–2,400 B removed per kept event. Sinks must not retain the record and must be concurrency-safe (watchdog/drainer may Write concurrently).

W5

Compiled runtime config

S/Mbreak

hc.Compile(Config) *Runtime — clamp, validate, resolve aliases, precompute policy lookup once at construction; fail fast on bad config. The finish path reads precomputed values only.

W6

Sampler v2

Sbreak

SampleInput drops Event, gains Lookup(key). Dropped events skip completion appends entirely — the ≤100 ns dropped path. All chain helpers keep signatures; error/panic retention unchanged.

W7

Single lifecycle

Mbreak

hc.Start + op.End(&err) only. BeginOperation/FinishOperation/OperationFinish and ~100 lines of hydration/reconciliation move internal or vanish. All integrations finalize through one path.

W8

Bridges rewrite

Mbreak

slog/zap/zerolog consume []Field in insertion order via native typed constructors — no zap.Any/slog.Any reflection, no key pools, no sorting; DeterministicOrder deleted. Adapter medium writes roughly halve.

W9

Field dedupe

Sbreak

op.* becomes the canonical lifecycle namespace. HTTP keeps http.method/path/route/status; op.code goes non-HTTP-only; worker drops its job.* mirrors. Mapping table published with the migration guide.

W10

Mini logger (deferred)

Madd

hc/log: Debug/Info/Warn/Error on the same forked encoder + writer, for ordinary non-request lines. Makes happycontext a one-stop logger — but the decision waits until the core lands and gets measured.

W11

Buffered sink (WAL drain)

S/Madd

Opt-in async drain: pre-encoded lines into a bounded ring, background batch writer, drop-oldest backpressure, Flush for shutdown. Sink call drops to ~100 ns regardless of destination health. Depends on W4/W8.

W12

In-flight records (data-gated)

Madd

Watchdog operation_stalled flush for operations exceeding a threshold, with eager operation_started as a per-domain policy option. Correlated by op.id. Makes OOM-kills and deadlocks visible.

Sequence

Every phase keeps the full test matrix green and carries before/after benchstat output in the PR. v0.5.0 exists so the forked encoder earns production trust before anything breaks.

v0.5.0 soft break¹

W1 encoder fork + golden/fuzz tests · W2 hc.NewJSONSink · remove the adapter sort machinery (DeterministicOrder + key pools, ~90 LOC across three modules) · remaining small compatible cuts. Default output bytes unchanged — the option was off by default; opt-in users get a loud compile error and migrate to hc.TestSink or pinned v0.4 adapters. Destination loggers cannot take over sorting (none offers it, and the map contract has already erased order) — the capability is removed, honestly.

v2 core PR coordinated break

W3 typed Event · W4 Record/Sink · W5 Compile · W6 sampler · W7 single lifecycle — one PR, because the storage change cuts across all of them.

v2 follow-ups module breaks

W8 bridges on []Field · W9 field dedupe + mapping table · W11 buffered sink · MIGRATION.md with before/after for every removed symbol · benchmarks refresh.

Later decided by data

W10 mini logger · W12 in-flight records · console/pretty output. The outcome-precedence fix (panic > error > explicit > 5xx > success) lands with a changelog callout.

10

Acceptance gates & rejections

Gates — every v2 phase

  • Benchmarks at 0 / 8 / 32 / 128 fields; sampling rates 0 / 0.05 / 0.5 / 1; policies 0 / 1 / 16 / 128
  • Enabled and disabled adapter levels; serial and parallel sampler runs
  • Golden equivalence: first-party sink output ≡ v1 zerolog-adapter output (modulo insertion ordering)
  • Encoder property test vs the zerolog table (random bytes + edge cases) — every micro-benchmark must pass it first
  • Encoder fuzzing — 1M execs in CI
  • All-module tests + -race; request-confinement tests replace concurrent-Event tests
  • Failure / panic / cancellation / timeout retention matrix stays green

Explicitly rejected

  • Pre-encoded JSON buffer as the Event store — nobody downstream could read fields without parsing
  • Forking zap or phuslu/log — larger core / no output continuity
  • sonic / goccy deps, assembly SIMD, jsontext as primary — see §05; pure-Go SWAR owns the hot path
  • A cache, a config framework, any new runtime dependency — still true from PERFORMANCE_PLAN.md
  • Durable disk-backed WAL — shipper territory (Vector, Fluent Bit); the crash window stays documented
  • Generics-heavy typed public API — Add(ctx, key, any) ergonomics stay; the type switch lives inside
  • Cross-module adapter codegen — previously rejected; the bridge rewrite shrinks the problem anyway

FAQ & glossary

The questions a reviewer asks, answered once — and the vocabulary the plan uses.

Why a slice instead of a map? Aren't map lookups O(1)?

Writes don't need random access — every hc.Add is an append. The map's O(1) lookup was only ever used by the sink clone and samplers, which read a handful of fields at most. Meanwhile the map costs hashing, boxing, growth rehashing, a clone per write, and random iteration order. The slice append is ~10 ns, deterministic, and zero-copy for every consumer. Lookup stays available for the rare read — a linear scan over a dozen records is faster than a map hashing a string.

Can I share an Event across goroutines?

Not on the fast path — v2 Events are request-confined: one writer, no lock, by contract. v0 allowed concurrent access under an internal mutex that every request paid for. If you must fan out, synchronize externally or clone the record view. Armed (stalled) events are the one internal exception — they switch to guarded mode, and that path is by definition the slow one.

Why change the Sink interface? My custom sink works.

The v0 contract forces a clone per kept event (the sink owns the map) and pushes every value through reflection-based conversion. The v2 Record is a read-only, ordered, typed view — zero copy for the sink, no reflection for bridges, and rec.Encoded() hands you finished bytes if that's all you need. Migration is one signature; the migration guide shows a before/after for a typical custom sink.

Why fork zerolog instead of just importing it?

We need ~800 LOC of append-only encoder, not a logger API — importing zerolog's surface (events, hooks, samplers, writers) to reach one internal package inverts the dependency. The fork is vendored with MIT attribution, property-tested, and sits behind an internal interface with a stdlib jsontext backend as the exit ramp if we ever want zero fork again.

Isn't drop-oldest in the buffered sink lossy?

Yes — deliberately. When the ring is full the alternative is blocking the request path (v0 behavior) or unbounded memory. Errors and panics bypass rate sampling, but buffering is deliberately uniform — during a genuine outage, downstream backpressure deciding what survives is the honest trade. Dropped counts are surfaced via hook, and Flush drains at shutdown.

Doesn't insertion order leak internal call order?

It exposes exactly what a reader wants: the order fields were attached, deterministic for a given code path and stable across runs of the same binary. That replaces v0's random map order papered over by an optional sort — v2 makes the natural order the only order and deletes the sorting machinery.

Why is a dropped event ≤ 100 ns and not zero?

Sampler decision (~7 ns), slot release, and pool return remain — plus the three completion records are never even appended, which is where the other ~500 ns of v0's dropped path went. Zero isn't achievable while the event still returns to a pool; ~100 ns is.

Why does field order matter at all? Why did v0 sort?

Three real needs: tests — golden/snapshot tests need stable bytes, and map-random order forces field-by-field parsing instead of a string compare; incident diffing — comparing two events reads as a clean field diff only when order is stable; downstream compression — shippers get better ratios when similar lines share byte layout. v0 needed the sort machinery because Go randomizes map iteration order on purpose, so a map-walk encode emits a different order every event — the pooled-key sort (replicated in all three adapters, +380 ns / +22% on slog medium writes) was the only fix, hidden behind an option because it cost speed. v2 makes the choice disappear: insertion order is the byte order — determinism becomes free, the option is deleted, and the order is more meaningful than alphabetical (header fields, user fields in attach order, completion last).

Why not let each adapter sort if its user wants it? Because someone must still pick an order when bytes get emitted — if the core doesn't, then every sink sorts independently: the same machinery replicated per adapter (v0's exact situation), inconsistent output across sinks for the same event, and custom-sink authors each reinventing it. Fixing order at creation is the only placement where it costs zero. Consumers remain free to reorder for display (zerolog's ConsoleWriter does exactly this), and the rare user who wants alphabetical bytes can wrap their sink in ~10 lines that sort rec.Fields() before delegating — a consumer concern, not core machinery.

Then why keep the sort at all before the break? We don't — v0.5.0 removes DeterministicOrder and its machinery a release early. Default bytes are unchanged (the option was off by default), opt-in users get a loud compile error, and stable-byte tests migrate to hc.TestSink or pinned v0.4 adapters. The one migration claim we must not make is "your logger can sort it": no host logger offers sorting, and the map contract has already thrown the order away by the time any logger sees a field.

What happens to my dashboards?

Field names change in exactly one place: worker job.* mirrors collapse into canonical op.*, and op.code goes non-HTTP-only. The mapping table ships with the migration guide, and a dual-write compatibility window is offered during the preview so queries can move before the old names disappear.

The feel — eight principles

  • ▸Two lines to adopt — Compile + middleware; misconfiguration fails at startup, once.
  • ▸Add reads as annotation, not logging.
  • ▸One event, always — header → handler → completion, deterministic by construction.
  • ▸Zero dependencies by default.
  • ▸Failures are sacred — errors and panics are never sampled away.
  • ▸The worst requests are the most visible — timeline for slow, operation_stalled for hung.
  • ▸Contracts printed on the box — three sentences, no fine print.
  • ▸Go-shaped — context-first, no fluent hot path, options only where earned.
