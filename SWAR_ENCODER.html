internal/hcjson · encoder deep dive

How the encoder uses SWAR

SIMD-Within-A-Register is the trick that lets the JSON string-escape scanner inspect 8 input bytes per iteration in pure Go — no assembly, no architecture tags — and it is used as a classifier, not an encoder: it never produces output bytes, it only decides when the byte loop can be skipped.

01

The one-paragraph answer

Every string that happycontext logs — record messages, field keys, string values — is encoded by hcjson.Encoder.AppendString / AppendBytes, a fork of zerolog's append-only JSON encoder. The dominant cost in that encoder is the escape scan: walking the string byte by byte and looking each byte up in a 256-entry table to decide whether JSON escaping is needed. The SWAR upgrade replaces that walk with a filter: strings of 16+ bytes are sliced into 8-byte words, each word is loaded into a uint64, and three bit-parallel predicates decide, in one pass over the register, whether all 8 bytes are "clean printable ASCII" (0x20–0x7e, except " and \). A clean string is appended in bulk between two quotes — zero per-byte work. Anything shorter or any word that trips a predicate falls back to the vendored zerolog table path, unchanged, so the emitted bytes are identical to the reference for every input (enforced by a 200k-case property test and CI fuzz).

Wait — isn't SWAR SIMD?

Yes: SWAR stands for SIMD Within A Register. It is the SIMD model — one operation applied to many independent data lanes — executed in an ordinary 64-bit register with scalar integer math, instead of on wide vector registers with dedicated instructions. Real SIMD (SSE/AVX/NEON) checks 16–64 bytes per instruction but needs assembly and per-architecture code; SWAR packs 8 bytes into one uint64 and reads each lane's verdict out of that lane's high bit (0x80) after broadcast subtractions. All lanes are processed in parallel in the sense that one word-level operation updates all of them — no vector registers, no assembly, portable pure Go. V2_PLAN §3b draws the same line, listing "True SIMD escaping (AVX2/NEON assembly)" as a separate, rejected option next to the adopted "pure-Go SWAR". Honest caveat: SWAR's ~4–6 register ops per 8 bytes are a small sequence of scalar instructions, not one SIMD instruction — the win comes from replacing ~8 table lookups + branches with a few register ops.

Where it is used — the callers

record.go routes everything string-shaped through the SWAR-capable appends: the message (record.go:75), string-kind fields (record.go:153), and error text (record.go:169) via the shared jsonEnc = hcjson.Encoder{} (record.go:177). Field keys go through AppendKey (hcjson.go), which calls AppendString itself. The JSON sink writes each record's Encoded() form in one Write (json_sink.go:32). The encoder is a stateless value type, so the SWAR path is exercised on every log line, by every goroutine, with zero shared state.

02

The problem: escaping is a scan

JSON strings need escaping for a small set of bytes. The fork's noEscapeTable (string.go, vendored verbatim) classifies every byte:

Byte classRangeJSON outputTable path handling
0x20 – 0x7e, not " \printable ASCIIas-isone table lookup, pass
0x22 0x5c" \\" \\backslash prefix, complex path
\b \f \n \r \twhitespace controls\b \f \n \r \tshort escape, complex path
0x00 – 0x1f, other; 0x7fcontrol bytes, DEL\u00xxhex escape, complex path
0x80 – 0xffnon-ASCII / UTF-8valid runes raw, invalid \ufffdrune decode, complex path

Note the trap: 0x7f (DEL) is not clean — zerolog's table escapes it — even though it sits inside the ASCII printable range. Any SWAR scan that naively accepts <= 0x7e "plus 0x7f" is wrong; the range predicate below is built specifically so that ≥ 0x7f trips a subtraction underflow. (V2_PLAN lists this as a hard-won correctness note.)

The reference implementation (appendStringTable, vendored verbatim from zerolog) pays one table lookup plus a branch per byte; when it hits a byte that needs escaping it hands off to appendStringComplex for the rest. For log payloads — URLs, paths, messages — the overwhelmingly common case is a string where every byte is clean, so the encoder burns a lookup per byte purely to discover "nothing to do". At 96 chars that measured ~31 ns (zerolog table, M4). The SWAR work exists to make that discovery ~8× cheaper per byte: ~25 ns, ≈ −18% (V2_PLAN §3b table, reproduced in §9).

03

The hybrid: SWAR as a filter in front of the table

SWAR is used only as a pre-filter. The real encoder — escaping rules, \u hex, UTF-8 rune handling, \ufffd replacement — is the untouched zerolog table path, which doubles as the correctness oracle. The SWAR code can only answer one question: "is this string clean enough to append verbatim?" Its answer is a boolean; if true, the string is quoted and bulk-appended in three appends:

// internal/hcjson/string.go — the whole fast path
func (e Encoder) AppendString(dst []byte, s string) []byte {
    if len(s) >= swarMinLen && isCleanASCII(s) {       // gate: 16+ bytes, SWAR scan
        return append(append(append(dst, '"'), s...), '"')  // quoted bulk append
    }
    return appendStringTable(dst, s)                    // oracle / fallback
}

Two properties make this division of labor safe:

  • The SWAR path emits no escape logic of its own. Its only output action is append(s...) between quotes, so the moment it is wrong, output differs from the table path — which is exactly what the property and fuzz tests compare (byte-identical, 200k generated strings + CI fuzz, §10).
  • The filter is conservative. A false "dirty" verdict sends the string to the table path, which re-scans it and produces correct output. Only a false "clean" verdict (a miss) could corrupt output — and the predicates are engineered so a miss is impossible (§5–§8).
Why hybrid and not pure SWAR

If the scan were forced on every string, dirty strings would pay twice: a doomed SWAR scan followed by the full table re-scan. The prototype measured exactly that loss — escape-heavy strings went 22.2 → 25.4 ns — while short keys (7 chars) also got slower (4.8 → 5.2 ns) because scan setup outweighed the 7 lookups it saves. Hence the two gates: len >= 16 for the scan at all, and scan-then-bulk-append only when the scan says clean. Clean ASCII is the dominant log shape, so the hybrid keeps the −11…−18% win where it pays and never taxes the minorities.

The length gate is pinned by a test: TestAppendStringSWARBoundary verifies that a 15-byte string with a NUL goes through the table path and a 16-byte one engages the scan (its escape is caught by the SWAR predicates instead).

04

Chunking: eight bytes, one register

The scanner (isCleanASCII in string.go; the []byte twin isCleanASCIIBytes in bytes.go) consumes the input 8 bytes at a time. Each chunk is loaded as one little-endian uint64 and handed to chunkIsClean; whatever tail remains after the loop is checked byte-by-byte against the same noEscapeTable the table path uses:

func isCleanASCII(s string) bool {
    for len(s) >= 8 {
        if !chunkIsClean(binary.LittleEndian.Uint64([]byte(s[:8]))) {
            return false                    // one word in, verdict out
        }
        s = s[8:]
    }
    for i := 0; i < len(s); i++ {           // tail: fewer than 8 bytes left
        if !noEscapeTable[s[i]] { return false }
    }
    return true
}

One chunk = one uint64; byte 0 lands in the least-significant lane. The predicates treat every lane identically and independently, so lane order only matters for borrow propagation (§5), never for which bytes get checked.

Because each 8-byte window is judged on its own word, a special byte straddling a chunk boundary is simply the first lane of the next chunk — chunk-local predicates can't lose it. Tests pin specials at positions 6, 7, 8, 9, 14–17 and 22–23 to prove boundary safety. Unaligned uint64 loads are fine on every platform Go targets (amd64/arm64 allow them), and the whole scan is allocation-free — the benchmark shows 0 B/op, 0 allocs/op.

Byte-slice input mirrors this exactly: AppendBytes gates on the same swarMinLen and shares chunkIsClean, so both entry points get the same fast path from one implementation.

05

Predicate 1 — "printable ASCII": the range trick

chunkIsClean (string.go) first asks whether all 8 bytes are in [0x20, 0x7e]. The one-liner does it with two broadcast subtractions and an OR:

// ((x - 0x2020202020202020) | (0x7e7e7e7e7e7e7e7e - x)) & 0x8080808080808080
if ((x-0x2020202020202020) | (0x7e7e7e7e7e7e7e7e-x)) & swarHighs != 0 {
    return false // control (<0x20), DEL (0x7f), or non-ASCII (>=0x80)
}

The mechanism, lane by lane. A lane's high bit (0x80) is the "flag" the final mask reads. Subtract a broadcast constant from the whole word: in each lane, an underflow sets the high bit of the result, because e.g. 0x09 − 0x20 = −0x17 wraps to 0xe9. So:

  • Term 1, x − 0x2020…: a byte below 0x20 (control character) underflows and flags its own lane — and then borrows into the next-higher lane, which is exactly how arithmetic lets a dirty byte disturb its neighbors (§8 explains why that is safe).
  • Term 2, 0x7e7e… − x: a byte above 0x7e — DEL 0x7f and everything non-ASCII — underflows the mirrored subtraction and flags its lane. This is what keeps 0x7f out of the clean set.
  • The OR + mask merges both verdicts; any flagged lane anywhere rejects the chunk.

"GET\t/api" as one word: the tab underflows term 1 and flags its own lane; the space in lane 4 inherits a borrow and gets a false flag (0xff). The verdict is already "dirty" — the FP changes nothing.

Why the double subtraction can never miss: every out-of-range value leaves a high bit in at least one term. The interesting edge is what a borrow can destroy — a borrow into a lane can strip the high bit only when the no-borrow result is exactly 0x80. Term 1's no-borrow result is 0x80 only for byte 0xa0 (whose mirror term underflows hard), and term 2's is 0x80 only for byte 0xfe (whose forward term lands at 0xde, high bit set); even 0xff, whose mirror term alone lands at 0x7f and never flags, is caught by term 1 at 0xdf. No byte value puts both terms at exactly 0x80, so at least one term keeps its flag for every byte outside the range — controls, DEL, and all non-ASCII.

06

Predicate 2 — "no zero bytes": the load-bearing canonical form

Both remaining dirty bytes — " and \ — are checked with an exact per-value search: XOR the word with a broadcast copy of the byte, then ask whether any lane became zero. That reduces "find a quote" to "find a zero byte", and the zero-byte detector is the sharpest edge in the whole file:

// hasZero64 — this MUST stay in the canonical SWAR form.
func hasZero64(x uint64) bool {
    return (x-swarOnes)&^x&swarHighs != 0   // (x - 0x0101…) &^ x & 0x8080…
}

Subtract 1 from every lane at once (0x0101…). A zero byte underflows and flags its lane, and the borrow propagates up through a run of zeros, flagging each. Three variants matter, and only the canonical one is correct:

VariantBehaviorVerdict
(x − ones) & ~x & highsflags every zero lane; the &~x clears the spurious flags that bytes ≥ 0x81 raise (see below). Residual false positives exist but only sit directly above a true zero (§7). canonical — this is what runs
(x − ones) & highs"simplified" by dropping &~x — still never misses a zero, but now every byte ≥ 0x81 also flags, because e.g. 0xf0 − 1 = 0xef keeps its high bit without any underflow. In this encoder's context every such chunk is already dirty (non-ASCII), so it is merely slow and noisy. wrong — FP storm on UTF-8
(x − ones) & x & highs"simplified" by swapping &^ for & — the fatal one. A zero byte has no high bit in x for the AND to preserve, so the mask wipes out exactly the lanes that matter: it never detects a zero. Real quotes and backslashes sail through as "clean", escaping is silently skipped, and the output is corrupt JSON. fatal — detects nothing
The incident that made this a gate (V2_PLAN §05 / §3b)

The first SWAR prototype benchmarked 3× faster than everything — because a subtly wrong zero-byte detector (the & variant above) meant it never flagged anything and skipped escaping entirely. Benchmarks smiled; output was corrupt. Only the 200k-case property test against the vendored table path caught it, which is why equivalence + fuzz tests are hard gates for W1, not nice-to-haves — and why the code comment and test suite both treat the canonical shape as load-bearing. The property test fails any regression that reintroduces the bug.

The &~x term's true job, demonstrated by the "dropped" row: subtracting 1 from a byte ≥ 0x81 leaves the high bit set without any underflow — a machine-level false positive that has nothing to do with zeros. Those bytes are exactly the ones whose own high bit is set in x, and &~x removes precisely them. Exhaustive and random checks confirm the canonical form flags: every true zero lane, plus benign borrow artifacts whose chain always starts at a true zero.

07

Predicate 3 — exact search for " and \

With a zero detector in hand, finding a specific byte value is an XOR away (hasValue64):

// hasValue64 reports whether any byte of x equals the broadcast byte c,
// via the canonical zero detector on the XOR mask.
func hasValue64(x, c uint64) bool { return hasZero64(x ^ c) }

// in chunkIsClean:
return !hasValue64(x, swarQuote) && !hasValue64(x, swarSlash)  // 0x22…, 0x5c…

A byte equal to the target becomes XOR-zero and is caught exactly. The comment in the source flags one tempting but unsound merge: AND-ing the two XOR masks — hasZero64((x^quote) & (x^slash)) — looks like one pass but is wrong, because an ordinary byte whose quote-XOR and slash-XOR have disjoint high-bit patterns can AND to zero and masquerade as "no match". The two searches stay separate. (Why the AND fails: each zero detector reports via the high bits of its subtraction, and the two subtractions place their evidence in different bit positions; the intersection can be empty even when a match exists.)

Borrow-chain false positives carry over from §6: a byte whose XOR-lane is 0x01 sitting directly above a real match lane is flagged too. For the quote search that byte is 0x22 ^ 0x01 = '#'; for the slash search, 0x5c ^ 0x01 = ']'. In the composed scanner these FPs are inert: they occur only in a chunk that already contains the real match, so the chunk is rejected anyway — and the FP never flips a clean chunk to dirty (§8).

08

Composition: why the chunk verdict is trustworthy

chunkIsClean chains the three predicates in a fixed order — range first, then quote, then slash. The order matters: the quote/slash searches only ever run on words already proven printable, which caps their XOR-lanes at ≤ 0x5c and keeps the §6 &~x analysis airtight. The verdict composes to a strong property:

Verified: no misses, and no false positives on clean chunks

For this write-up the predicates were checked directly against a byte-exact oracle: 0 misses and 0 false positives across (a) all 16.7M possible 3-lane patterns embedded in an otherwise-clean word — 1.9M of them fully clean — (b) 5M random full-width words drawn only from the 93 clean byte values, (c) 400k random words, and (d) 200k words with dirty bytes planted at every lane position. The scanner behaves as an exact filter on 8-byte chunks: reject ⟺ the chunk contains a byte needing escape.

The mechanism behind the exactness, lane by lane: the only lanes a predicate can flag falsely are those above a borrow chain, and every borrow chain starts at a lane that genuinely underflows — a byte < 0x20 in term 1, ≥ 0x7f in term 2, or an XOR-zero (a real quote or slash). Chain starters always flag their own lane, so a chunk with any dirty byte is rejected at that byte; lanes above it may add false flags that change nothing. Conversely, a chunk with no dirty byte has no chain starter anywhere, so nothing flags: FP requires dirt, and dirt always flags. Misses would need a dirty byte whose every term keeps its high bit clear — ruled out by the "exactly 0x80" argument in §5 and the underflow-always-flags argument in §6.

The source comments are deliberately more cautious than this — "conservative: any suspicious chunk returns false", "false positives only send the string to the table path" — because the predicates in isolation (especially hasZero64 as a standalone detector, exercised directly by tests) do have the borrow FPs; only their composition on full words makes them inert. That caution is the correct engineering posture: the cost of a theoretical FP is a slower fallback, the cost of a miss is corrupt JSON, so every comment and test tilts toward "when in doubt, table".

Ratio on the gate payload: 61.8 / 50.6 ≈ −18%, matching the documented prototype number, and the v2 gate ("escape, 96-char clean ASCII ≤ 26 ns", V2_DESIGN §4) was met during W1. Absolute ns vary run to run; the ~18% table-vs-SWAR gap is stable.

The design deliberately stops at pure-Go SWAR: true SIMD escaping needs per-architecture assembly (AVX2/NEON, as in goccy or sonic), splits the codebase by build tag, and only touches the slice of escape cost that remains after SWAR already captured the 11–18%. V2_PLAN §3b's verdict: revisit only if post-v2 profiles show the escape scan above ~5% of lifecycle time. Sonic/goccy were also rejected as dependencies on measurement — the fork's typed append loop beats them by ~140× on the only payload where a marshaler could appear, so the SWAR-in-pure-Go hybrid owns the hot path with zero dependencies and zero assembly.

Reading the numbers honestly

SWAR wins only on clean ASCII ≥ 16 bytes, and it wins by skipping work, not by doing it faster — a clean 96-char string costs roughly one scan (≈8 word-checks of ~4 ops each) plus a bulk append, against 96 table lookups. Dirty strings pay the scan plus the table re-scan, which is why escape-heavy payloads show a small loss and the gate length is 16. Log payloads are dominated by the clean shape, and the two benchmark guards (TestGatePayloadsTakeFastPath) exist precisely so the headline benchmark can never silently drift onto the table path and keep claiming a SWAR win.

The safety net — tests that pin every claim

  • Property gate — 200,000 generated strings (TestAppendStringProperty): random bytes, clean ASCII with injected specials at random positions, multi-byte UTF-8, and systematic adversarial placements must encode byte-identically through the hybrid SWAR path and the vendored zerolog table reference. The header comment is blunt: "No benchmark result counts until this passes (V2_PLAN §05)."
  • CI fuzz — 60 s per target (fuzz_test.go): the differential oracle plus a second, semantic one — output must always be valid JSON and must round-trip to the input when the input is valid UTF-8. The round-trip closes the class a differential-only oracle cannot see: a byte class both paths mishandled identically. Seeds include the SWAR boundaries (15 vs 16 bytes, 23 + NUL, 31 + quote/slash) and the gate URL.
  • Predicate unit tests (TestChunkDetector): every special byte value planted at every one of the 8 lane positions; the canonical zero detector never misses and never invents zeros on clean words; and a carry-chain regression set — long 0xff/0xfe runs, boundary bytes 0xa0/0x80 — "found by the fuzz corpus", covering the borrow shapes §5–§7 reason about.
  • Boundary pins: TestAppendStringSWARBoundary (15/16 gate), specials straddling chunk edges at positions 6–9, 14–17, 22–23, and TestGatePayloadsTakeFastPath — the benchmark payloads must actually take the path they claim to benchmark (96-char URL SWAR-clean; the escape-heavy payload must not be).
  • Fuzz corpus as regression memory: the carry-chain chunks in TestChunkDetector are quoted as "found by the fuzz corpus" — inputs that once confused naive (x+ones)-style checks live on as permanent unit tests.
